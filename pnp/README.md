# PNP-lite: policy decisions without fine-tuning

A structured policy names its conditions and lists if/then rules over them. Laya answers each
condition as a yes/no (`noul`) question about the state, all in one call, and plain code applies
the rules. Laya does the perception; the logic is exact by construction.

```python
import laya
from pnp.policy import Policy

policy = Policy.from_dict({
    "conditions": {
        "authorized": "Is the activity explicitly authorized, scheduled or approved?",
        "stolen_creds": "Is there evidence that an account's credentials were stolen?",
        "malware": "Is there evidence of malware or ransomware running on a host?",
        "suspicious": "Is there any unusual or suspicious activity?",
    },
    "rules": [
        {"if": "malware or (stolen_creds and not authorized)", "then": "contain"},
        {"if": "suspicious and not authorized", "then": "investigate"},
    ],
    "default": "close",
})
agent = laya.load("weights/laya", subfolder="typed-decisions")
result = policy.decide(agent, "EDR: a process is encrypting files on FIN-WS-22 ...")
result["decision"], result["rule"], result["conditions"], result["probability"]
```

`probability` is P(decision) from the condition probabilities, treating them as independent and
enumerating every truth assignment.

## Experiment

`python -m pnp.evaluate` compares three approaches on 36 hand-written cases across three policies
(security triage, refunds, a Minecraft agent), 12 cases each. Every case labels the truth of each
condition; the correct decision is the policy run on those labels.

- **plain**: one `choice` question listing the decisions with short descriptions.
- **prompted**: the same question with the whole policy written into its instructions
  (`max_len=1024`, `head_max_len=512` so it fits).
- **pnp**: the conditions as `noul` questions, the rules applied in code.

Decision accuracy, CPU (4 cores), local weights, no fine-tuning:

| checkpoint | plain | prompted | **pnp** | condition accuracy | pnp ms/case |
|---|---|---|---|---|---|
| english | 0.31 | 0.28 | **0.67** | 0.78 | 654 |
| typed-decisions | 0.31 | 0.36 | **0.69** | 0.83 | 606 |
| multilingual | 0.39 | 0.31 | **0.50** | 0.70 | 228 |

By policy (typed-decisions): security 0.25 / 0.25 / **0.83**, refunds 0.33 / 0.50 / **0.67**,
Minecraft 0.33 / 0.33 / **0.58**.

Writing the policy into the prompt does not help: the checkpoints were not trained to follow
rules given in their input. Splitting it into conditions roughly doubles accuracy.

The remaining errors are all perception, since the logic cannot be wrong. The conditions missed
most often are `recent` (dates: "bought in January, it's June"), `low_health` and `hungry`
(numbers such as "Health 4/20"), and the vague `suspicious`. Every rule that fires needs each of
its conditions right, so condition errors compound.

## Limits

- 36 cases, written for this test, one run each. Treat differences under about 15 points as noise.
- The cases are short and clear-cut; real alerts and tickets are longer and messier.
- Conditions are treated as independent when computing `probability`; correlated conditions make it
  over- or under-confident.
- The 0.5 threshold is not tuned per condition.

## Next steps

- Extract numeric and date conditions with code (regex or a parser) and keep Laya for the fuzzy ones.
- Tune each condition's wording and threshold on a few labeled examples.
- A larger, independently written test set, including longer states.
- The fork from the original idea: train once on (policy, state, decision) triples generated by
  running random policies, and check whether it beats this baseline on policies it never saw.
